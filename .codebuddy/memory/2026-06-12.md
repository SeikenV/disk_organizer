## Ollama 模型 Benchmark（4 模型对比）

**任务**：用 scan.snapshot.json 对 4 个 Ollama 模型跑相同 enrichment 测试，对比速度和文本效果。

**脚本**：`scripts/bench_models.ps1`，结果在 `logs/2026-06-12_09-26-02/`。

**速度结果**：
| 模型 | 耗时 |
|------|------|

| Qwen3-0.6B-Distilled | 104s |

**结论**：`qwen3.5:0.8b` 是最佳平衡点。

## Qwopus3.5-0.8B 模型测试（放弃）

- 从 ModelScope 安装 `Jackrong/Qwopus3.5-0.8B-v3-GGUF` (Q4_K_M, 529MB)
- 去掉 JSON Schema 约束解码（`format` → `None`），改为纯文本 + 客户端解析
- **单请求 ~29 秒**（`/api/chat` 和 `/api/generate` 一样慢）
- `REQUEST_TIMEOUT` = 30s，卡在边界导致大量超时
- 根因：推理蒸馏架构，空 `<think></think>` 块也要走完整推理流水线
- 输出格式：`<think>\n\n</think>\n\n{"category": "...", "purpose": "..."}`，`parse_summary` 第二步 `{`...`}` 兜底能解析
- **结论**：不适合批量分类场景，qwen3.5:0.8b (~2s/请求) 是最优选择

## Qwopus 深度优化尝试（最终放弃）

在确认原生 29s 太慢后，尝试了一系列优化：
- 切换到 `/api/generate` 端点（替代 `/api/chat`）
- 极简 system prompt 压缩到一行
- 去掉 `num_predict` token 限制（本地模型按时间控制即可）
- 添加 `strip_think()` 解析层去掉 `<think>...</think>` 块

**结果**：极简 prompt 下 4.1s 完成，但分类质量差（说项目源码可以删）。加回安全规则后 think 块爆炸，60s 超时。推理蒸馏模型的 `<think>` 对 prompt 长度高度敏感——规则一多就失控。

**最终决定**：放弃 qwopus，回归 qwen3.5:0.8b。保留 `/api/generate` + `strip_think` + 不限 token 等改进（对所有模型适用）。
